# AegisAI v2 — Decision workspace

## Current release: 2.1

Start with [START_HERE.md](START_HERE.md) for the tested setup, demo route and
release evidence. See [ARCHITECTURE.md](ARCHITECTURE.md) and
[PORTFOLIO.md](PORTFOLIO.md) for design tradeoffs and accurate project wording.
Live approval now requires a human checklist acknowledgement. The experimental
same-model consistency reviewer is disabled by default after missing known
development defects. The app remains a local portfolio prototype with documented
reasoning limitations, not a validated automated decision system.

## Evaluation upgrade

Includes a 30-case synthetic benchmark, separate development/held-out splits,
an Ollama evaluation runner, quotation checks, failure accounting, latency
measurements and a human-review rubric. See [evaluation guide](evaluation/README.md).
Check the dataset without Ollama: `python evaluate.py --check --split all`.
Run the development split after setup: `python evaluate.py --split development`.
Results are saved separately from your application database. No live benchmark
results or answer-quality claims are supplied with this upgrade.

A local, single-user application for structured decision reviews. Rebuilt from
Priyansh's AegisAI Decision Guardrail prototype. Python/FastAPI, Pydantic,
SQLite, vanilla JavaScript and local Ollama. No frontend build step or external fonts.

## Run

Python 3.10 or later is required. From this directory:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m uvicorn server:app --host 127.0.0.1 --port 8001
```

Open http://127.0.0.1:8001. On Windows, `./start.ps1` performs first-run setup
and starts the same server. If `python` opens the Microsoft Store, install Python
or use your installed Python executable in place of the first `python` command.

### Sample mode

Select **Explore samples**, choose one of three scenarios, and open the sample
assessment. No model is used. Briefs are locked to fixed fixtures, and reports,
reviews and exports remain labelled SAMPLE. Editing a sample for live assessment
requires switching to live mode. A sample does not demonstrate LLM quality.

### Live mode

Install Ollama from https://ollama.com and download the configured model:

```text
ollama pull llama3.2:3b
```

Ensure the Ollama service is running; if necessary, `ollama serve`. Then use
Live assessment. The default service is http://127.0.0.1:11434. Configure before
starting the server using environment variables:

- `AEGIS_MODEL`: installed Ollama model name (default `llama3.2:3b`).
- `AEGIS_OLLAMA_URL`: trusted Ollama service base URL (default local loopback).
- `AEGIS_DB`: SQLite file path (default `data/aegis.db`).

Briefs are transmitted to the configured model service; use a trusted endpoint.
The smaller default model is intended for local exploration. You can select a
larger installed model (for example `llama3`) using AEGIS_MODEL. Model quality and
latency vary by hardware, model and brief; the default has not been calibrated
against real decision outcomes. First generation can be slow while the model loads.
No automatic retries or
invented fallback scores are used. Model connection, timeout and output-validation
failures are saved as failed attempts without risk scores and cannot be reviewed.

## What changed

- Separate frontend and Python modules instead of one large embedded HTML string.
- Schema-constrained generation, strict integer ranges, required fields, and
  rejection of invalid output. Parsing JSON is no longer treated as sufficient.
- Per-risk likelihood/impact register, mitigation, monitoring signal and evidence.
- Exact quotation matching against submitted decision/constraints. Matching a
  quotation confirms its presence only, not the truth of its contents.
- Transparent deterministic scoring: highest likelihood × impact × 4.
- Cautious/Balanced/Flexible review thresholds and visible policy provenance.
- Assumptions, open questions, next steps and scenario outlook.
- SQLite reports, failed attempts and append-only application review events.
- Real local review actions with required reasoning and stale-review protection.
- Search/filter library, two-report comparison, Markdown and JSON downloads.
- Safe DOM text rendering, responsive layout, keyboard navigation, loading,
  empty, failure, success and offline-model states.

## Scoring policy

Likelihood and impact are integer ratings from 1 to 5, generated by the model
(or fixed fixtures in sample mode). Priority = likelihood × impact × 4.
Overall priority is the highest individual risk; averaging does not hide it.

Levels: LOW <32, MEDIUM 32–59, HIGH 60–79, CRITICAL 80–100.
Review threshold: Cautious 32, Balanced 48, Flexible 64.
At 80+, signal BLOCK; otherwise at the threshold, REVISE; below it, REVIEW.
Every assessment requires human judgment. There is no automatic approval.
These are ordinal priorities, not calibrated probabilities, confidence measures
or a validated prediction of real outcomes. Changing appetite changes the review
threshold, not the underlying risk ratings.

## Architecture / learning route

1. `static/index.html`: form and workspace structure.
2. `static/app.js`: request, loading states, report rendering and reviews.
3. `models.py`: accepted inputs and model output contract.
4. `agent.py`: Ollama call and independent output validation.
5. `policy.py`: deterministic scores, quotation matching and recommendation.
6. `store.py`: SQLite storage, review log and version conflicts.
7. `server.py`: API endpoints connecting these components.
8. `samples.py`: explicitly labelled fixtures for offline exploration.

Request flow: brief → validated request → Ollama → validated model output →
scoring policy → SQLite → report → human review → appended audit event.

The local API reference is at `/docs`, with the complete schema at `/openapi.json`.
The application intentionally blocks
cross-origin browser writes. Bind to loopback only. The local workspace has no
authentication, tenancy, encryption-at-rest, tamper-proof audit, external policy
integrations or production access controls. Reviewer names are user-entered, not
verified identities. Review actions do not execute external actions. Do not expose
this prototype as a shared service without implementing those controls.

## Tests

```powershell

.venv/Scripts/python.exe -m unittest discover -s tests -v
```

Tests use simulated model responses and a temporary SQLite database, never a
downloaded model or a real decision system. See `VERIFICATION.md` for actual
verification performed and remaining limits.
